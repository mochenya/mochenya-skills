# 学习架构：重点、依赖与进阶

用于陌生领域、宽主题、学习路线、教程取舍或多章知识材料。目标是让学习者知道什么值得优先理解、为什么，以及怎样沿主线推进，而不是生成完整术语目录。

## 根据目标建立主线

从当前请求与对话背景确定目标能力、主题边界、必要前置和可用实践条件。目标可以是阅读、使用、调试、解释或设计；同一主题在不同目标下的重要性与深度不同。

背景足够时直接提出合理路线，不先列长问卷。缺少的信息会改变学习方向时才询问，例如是为了使用工具还是理解其实现。

## 解释重点，而不只标注“核心”

优先识别以下节点，并说明选择理由：

- 能解释大量常见行为的核心模型。
- 连接语法、机制和工程实践的桥接概念。
- 后续多个主题共同依赖的前置。
- 容易形成错误直觉、且会导致反复误用的边界。
- 对当前任务有实际价值的语法、操作与工具能力。

对重要节点，按需说明它解释什么、缺少它会卡在哪里、后续在哪里复用，以及当前应理解到什么程度。“高阶”不是更偏门的 API，而是能处理更复杂的条件、机制和选择。

### 导航示例：从异步写法走向调度模型

学习者已经见过异步调用，却不知道接下来该学什么时，仅列出“协程、任务、事件循环、并发控制”仍然缺少指引。

更有用的导航是指出：需要理解目标环境中“谁负责调度、执行何时暂停、什么条件允许恢复”，才能解释执行顺序和阻塞影响；并发控制再联系受限资源及任务生命周期。若目标框架使用事件循环，它就是连接这些问题的关键节点之一。

这里演示的是如何说明重要性，不是跨语言统一的异步语义，也不是规定先穷尽调度器实现再写代码。具体概念与行为应依据目标语言和运行时。

## 组织前置与学习顺序

区分当前核心、必要前置、暂时借用、近期后续与远期扩展。按理解依赖形成主线，不照抄文档目录或 API 字母顺序。

学习顺序不必等于知识的严格推导顺序：可以先用简单现象建立问题，再引入解释它的模型；关键是在正式推理依赖某个概念前，让学习者获得足够理解。

不要把所有相关基础设成入门门槛。能以有边界的阶段性模型进入实践时，明确当前模型的范围，并安排后续加深。

## 多章材料才需要覆盖与归属管理

批量写作或课程规划时，用轻量清单检查：

| 内容 | 首次讲解与前置 | 为什么重要、后续复用 | 能力证据 |
| --- | --- | --- | --- |
| 核心概念或操作 | 哪章负责，依赖什么 | 支撑什么理解或任务 | 能解释、预测、操作或选择什么 |

清单用于发现遗漏与重复，不要求作为每篇回答的可见表格。覆盖既包含概念，也包含目标所需的操作；不以章节数量或 API 数量衡量质量。

一章围绕连贯问题、模型或操作族。独立机制、不同前置或不同完成能力适合拆章；同一操作族不机械地按一个方法一篇拆散。持续复用的核心概念应在新情境中加深，而不是每章重复定义。

## 用能力安排进阶

根据当前阶段，选择从示范到独立应用的必要活动：

- 根据规则预测并解释一个结果。
- 改变条件，判断结论是否仍成立。
- 不照抄示例，完成修改、实现或故障分析。
- 比较方案，在约束下说明选择与代价。

路线可以给出自检入口；只有实际观察到表现，才能判断学习者是否达到阶段目标。没有反馈时，描述应达到的能力，不宣称已经掌握。

## 资料与进一步展开

教材和教程可帮助安排学习顺序；规范与官方参考支持语义和保证，正式设计材料支持设计依据，目标环境实验支持具体表现。资料冲突时先区分版本、抽象层与适用条件，不把一种实现推广为普遍规则。

需要整门语言的专用覆盖检查时，参见 [编程语言学习](programming-language-learning.md)；需要操作族覆盖时，参见 [语法与操作](syntax-and-api-teaching.md)；需要诊断具体理解障碍时，参见 [概念建模](concept-first-teaching.md)。不要仅因规划中提到相关主题就加载所有细则。
