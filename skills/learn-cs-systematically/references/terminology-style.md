# 中文专业术语与语言规范

以专业、准确的简体中文作为主要讲解语言。

## 根据专业语境选择译法

按照以下优先级选择中文术语：

1. 正式标准或规范采用的译法。
2. 该领域权威中文教材稳定采用的译法。
3. 官方中文文档采用的术语。
4. 相关工程生态中已经稳定使用的译法。
5. 没有可靠译法时，保留英文原词并给出中文解释。

不要逐字硬译。如果字面翻译与领域惯用语冲突，应以专业语境为准。

例如：

- 在数据库领域，transaction 应译为“事务”，不能使用日常语境中的“交易”。
- concurrency 使用“并发”，parallelism 使用“并行”，不能合并成同一个概念。
- React Hook 是相关生态中的正式术语，不应为了汉化而创造生硬的字面译法。

## 核心术语首次引入

每篇独立回答、笔记或导航文档分别计算首次引入。对主概念、必要前置知识、骨干概念、桥接概念和当前解释必须依赖的其他核心术语，在解释性文本中第一次承担解释作用时，使用：

```text
英文正式术语（中文规范译名：准确、简炼地定义它是什么）
```

例如：

```text
type predicate（类型谓词：函数返回类型中形如 `value is T` 的类型标注，表示函数返回 `true` 时，TypeScript 将 `value` 视为 `T`。）
```

首次定义应当建立四个对应关系：英文正式名称、中文规范名称、准确的“是什么”定义，以及概念在规范、代码或运行时中的真实表达。对于具有自然代码、类型签名、命令、数据结构、伪代码或状态表示的概念，优先在首次定义附近给出最小真实表达；不要用抽象的“某种机制”替代可直接观察的形式。

首次定义只负责术语锚定和准确释义，不把动机、系统角色、完整机制、边界或工程建议全部压进括号。主概念仍须在后文分别解释这些内容。

完成首次定义后，默认使用中文规范名称；只有在术语对比、消歧、检索或强调原文时，才使用“中文规范名称（English term）”。不要反复书写带完整定义的双语格式。

每篇持久笔记都应能够独立阅读：即使另一篇笔记已经介绍过英文名，本篇第一次解释该术语时仍应重新标注。

## 保留技术文本原样

以下内容不要翻译或擅自修改：

- 产品名和项目名。
- API、函数、类、方法和包名。
- 命令、参数、配置键、协议字段和错误码。
- 编程语言关键字和 SQL 关键字。

在 Markdown 中，标识符和字面命令使用行内代码格式。

## 中英文排版

- 首次引入核心术语时使用中文全角括号：英文正式术语（中文规范译名：准确释义）。
- 保留英文术语的官方大小写。
- 中文与相邻英文单词或数字之间按可读性保留一个半角空格。
- 中文正文使用中文标点。
- 首次定义之后默认使用中文名称；需要对照原文时才使用中文名称（English term），不要在每次出现术语时重复双语形式。

## 真实表达优先

首次定义附近应优先展示概念的最小真实形态：

- 编程语言和类型系统使用语法形式、类型标注或函数签名；
- API、命令和配置使用最小调用或配置形态；
- 数据结构使用字面结构、节点关系或关键字段；
- 算法使用最小伪代码、输入输出或不变量；
- 运行时机制使用事件序列、状态转换或调用关系。

没有自然的代码或形式化表达时，使用准确的规范关系、公式、状态或最小反例；不要为了满足格式强行添加无关代码。真实表达用于让读者看到概念“长什么样”，不能替代后文对动机、机制、边界和验证的完整讲解。

## 处理多个常见译法

同一英文术语存在多个常见中文译法时：

1. 根据当前领域选择一个规范名称。
2. 创建笔记时，将有搜索价值的其他译法放入 aliases 或术语表。
3. 在同一回答和整个 Vault 中保持规范名称一致。
4. 只有译法本身会影响理解时，才解释选择理由。

不要无理由地让不同笔记交替使用不同译法。

## 规范性措辞

有意识地区分以下词语：

- **必须**：正式强制要求、逻辑必然、正确性必要条件或明确的项目硬性规则。
- **应当**：具有合理例外的强建议，包括规范中的 SHOULD。
- **建议**：有理由的工程推荐，不表示普遍强制。
- **可以**：表示具备能力或允许选择，不自动表示推荐。

使用“行业标准”“最佳实践”“生产环境必须”和“通常都应该”等表达时，补充适用生态、场景、依据和边界，不能借模糊权威代替论证。

## 表达风格

- 先给结论。
- 使用具体因果关系，不依赖模糊权威。
- 重要条件尚未说明时，不使用“显然”“很简单”或“只要……就……”。
- 明确标注不确定性和版本依赖。
- 保持专业、解释性的语气，不为了显得学术而堆砌术语。
