# 专业术语与准确表达

用于专业译法选择、缩写消歧和规范性措辞。目标是准确、可理解、可检索，不是增加双语标注的密度。

## 名称、定义与真实表达

引入当前解释依赖的新概念时，提供准确名称与足够的“是什么”定义；英文名有助于检索或消歧时一并给出。有自然代码、签名、节点结构或状态表达时，可放在定义附近帮助识别概念。

可采用“中文名（English term）”或先定义后注明原文，不强制把名称、定义、动机、机制和边界全部塞进一个括号。定义应说明类别与区别，避免用“某种机制”“一种方式”循环解释。

连续对话可以承接已经建立的名称与含义；复习只在需要唤起或消歧时重述。独立笔记应让目标读者找到核心术语及含义，但不必重教全部前置知识。术语映射不能代替概念之间的关系说明。

## 选择译法与保持一致

- 使用当前领域通行且准确的译法，不把日常含义直接套入专业语境。
- 译法不统一时，选择一个适合当前语境的名称，并在有歧义时附英文。
- 不为了汉化而创造生硬的新词；没有稳定译法时保留原文并解释。
- 在当前回答或授权编辑的笔记集合中保持一致，不为统一译法擅自扫描整个 Vault。
- 持久笔记中的其他常见译名或缩写，可放入 aliases 以便检索。

例如，数据库中的 transaction 是“事务”；concurrency 与 parallelism 分别为“并发”与“并行”，不能因日常语言相近而合并概念。

## 保留技术文本

产品名、API、函数、类、方法、包、命令、参数、配置键、协议字段、关键字和错误码保持官方拼写及大小写。标识符与字面命令使用行内代码。

中文正文使用中文标点，混排以可读性为准；不反复附上已经明确的双语名称。

## 结论强度与依据

- “必须”：正式强制要求、逻辑必要条件或明确的项目硬性规则。
- “应当”：允许合理例外的强建议；解释规范中的 SHOULD 时保留其上下文。
- “建议”：有条件的工程选择，需要说明理由。
- “可以”：能力或许可，不自动表示推荐。

区分“规范保证”“当前实现如此”“在这些条件下通常如此”和“建议如此”。使用“最佳实践”“生产环境必须”等措辞时，给出适用条件与依据，不借模糊权威代替分析。

重要条件尚未说明时，不用“显然”“只要……就……”掩盖推理缺口。准确不要求枯燥：具体对象、因果关系和恰当例子比堆叠术语更有解释力。
