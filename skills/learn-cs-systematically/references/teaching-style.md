# 教学与讲解表达规范

系统讲解、章节式教学或持久笔记需要组织正文时使用本规范。本文件决定内容怎样呈现、标题怎样承载推理和何时拆分；不决定某个领域必须覆盖哪些概念或 API。

## 先给答案，再建立推理

正文第一部分先给出当前范围内最重要的结论，随后说明它解决的问题、依赖的模型、决定结果的机制和关键边界。不要用长篇背景、诊断问卷或 API 清单推迟已经明确的问题。

常见推进顺序是：

```text
核心结论
→ 要解释的问题
→ 准确概念与基本模型
→ 运行或推导过程
→ 可观察证据
→ 边界与相近选择
→ 工程使用或下一步
```

这是内部组织线索，不是必须原样显示的章节模板。按主题删除、合并或调整不需要的部分。

## 用标题表达具体问题或判断

标题应让读者只看目录也能知道推理怎样前进。优先使用：

- “为什么普通函数的 `this` 由调用方式决定”；
- “箭头函数为什么不创建自己的 `this`”；
- “`Move` 如何改变两个绑定的有效状态”；
- “`slice` 与 `splice` 分别改变了什么”；
- “什么时候借用比克隆更合适”。

避免把内部检查项机械地写成：

```text
核心概念
运行机制
完整示例
工程迁移
```

“概念、机制、证据、边界、操作契约、工程选择”用于检查内容是否完整；最终标题应尽量表达当前主题中的真实问题、因果关系、状态变化或选择条件。

每个二级标题只推进一个主要判断。标题下面第一段尽快回答该标题，不先重复标题或铺陈无关背景。

## 保持一条可追踪主线

- 复用一个连贯场景、数据集或程序，减少不必要的上下文切换；
- 单一机制优先使用一个代表性示例和少数高价值变式；
- 一组方法具有不同契约时，允许围绕同一数据使用多个短示例，不能用一个方法替代整个操作面；
- 高级分支只有在决定当前结论时展开，否则明确列为后续；
- 链接只能扩展内容，不能替代读懂当前句子所需的定义和关系。

语法、数据类型、集合、标准库、API 或命令族的覆盖范围由 [syntax-and-api-teaching.md](syntax-and-api-teaching.md) 决定；可执行示例和输出由 [code-style.md](code-style.md) 约束。

## 按主题选择呈现结构

### 概念

围绕问题、准确定义、概念关系、基本模型、机制、证据和边界组织。核心地图用于暴露关系，不代替正文定义。

### 机制或系统

说明组件、初始状态、不变量、事件或调用顺序、数据流/控制流、可观察行为和失败情况。

### 算法

说明问题与输入输出、核心思想、不变量、逐步推演、正确性依据、复杂度及其前提、实现和边界。不能用复杂度结论代替算法解释。

### 编程语言特性

根据问题讲清为什么这样设计、实际怎样工作和工程中何时使用。设计背景、语义、实现和工程建议要区分；详细规则读取 [programming-language-learning.md](programming-language-learning.md)。

### 语法、API 或命令族

先按用途或生命周期分组，再解释调用形式、输入、输出和影响；使用导航表帮助比较，但表格不能代替必要的代码、结果和机制解释。

### 对比

先说明比较目的和判断维度，再比较结论。优先比较会改变行为或工程选择的差异，不按表面语法罗列无关项。

## 让示例承担解释责任

示例必须让学习者观察到当前主张，而不是只展示“正确写法”。代码或命令之后说明：

- 输入和初始状态是什么；
- 哪条规则决定关键步骤；
- 返回值、输出和原状态分别怎样变化；
- 哪个条件改变后结论会不同；
- 当前结果是规范保证、具体实现观察还是预期结果。

不要用代码注释机械翻译每一行语法。注释解释意图、机制、预期和边界，正文负责定义和完整推理。

## 谨慎使用类比和可视化

只有类比能映射到真实技术关系时才使用，并立即说明：

1. 类比中的对象分别对应什么技术实体；
2. 哪个动作对应什么规则或状态变化；
3. 类比从哪里开始不再准确。

真实比较或字段映射使用表格。当概念依赖、执行时序、状态迁移、层级、数据流、控制流或多分支选择仅靠短段落难以清楚表达，并且输出载体支持 Mermaid 时，建议使用 Mermaid 辅助说明；关系简单时优先使用短段落、列表或表格。

Mermaid 不能替代准确定义、机制讲解、代码示例、运行结果和关键边界，也不要用段落、表格、图和代码重复同一个简单结论。

## 表达工程建议

相关时说明：

- **建议**：在当前场景怎样做；
- **原因**：它保护什么约束或降低什么成本；
- **不这样做的后果**：具体的正确性、性能、安全性或维护问题；
- **适用边界**：什么条件下另一种选择更合理；
- **验证方式**：怎样通过测试、类型、监控或评审确认。

没有实际工程决策时，不强行添加生产规范或架构章节。

## 以完整性决定篇幅和拆分

篇幅是结果，不是目标。当前范围所需的定义、机制、核心操作、证据和边界优先于固定字数。优先保留一个共享同一问题、模型、示例和完成任务的连贯长章节；出现独立机制、不同前置或不同完成能力时再拆分。

内容太多时说明本篇完成什么、后续分别负责什么；不要静默删减，也不要为了显得系统把所有远期分支塞进同一篇。删除口语化填充、重复总结和装饰性结构，而不是删除决定理解的内容。
