# 编程语言学习：从设计问题到工程使用

学习一门新语言、解释核心语言特性、讨论“为什么这样设计”、建立语言课程覆盖，或进行跨语言语义比较时读取本规范。它负责语言特有的分析维度，不把所有计算机主题都强行解释成语言哲学。

## 三个核心问题

根据当前请求讲清：

```text
为什么这样设计？
它实际上怎样工作？
工程中什么时候使用？
```

这三个问题是分析方向，不是每篇回答必须显示的固定标题。D1 只展开决定当前结论的部分；系统讲解、课程章节和持久笔记再形成完整链路。

不要从 feature 清单开始。先恢复它面对的问题和约束，再解释选择、语义、机制、操作和后果。

## 整门语言的八个覆盖维度

以下八项用于规划和检查一整门语言课程有没有漏掉关键知识。它们不是固定章节顺序，也不要求每一章重复从语言哲学讲起。

### 1. 设计问题与价值取舍

Language design philosophy（语言设计哲学：一门语言对安全、性能、简单性、表达能力、兼容性和程序员责任等价值的总体优先级）用于概括长期方向。

Language design rationale（语言设计理据：把具体问题、背景约束、候选方案、最终选择及其代价连接起来的因果说明）用于解释某个特性为什么形成现在的设计。

至少判断：

- 语言最初或当前主要解决什么问题；
- 什么事情被设计为简单、显式、受限或禁止；
- 程序员、编译器和 Runtime 分别承担什么责任；
- 历史兼容、生态、平台和实现约束怎样影响选择；
- 当前解释是有一手资料支持的设计理据，还是教学推断。

不要用一句宏观价值观把所有语法事后解释成必然结果。

### 2. 计算模型与主要范式

Computational model（计算模型：用哪些抽象实体、操作和状态转换规则来描述计算）回答程序怎样表示和推进计算。

Programming paradigm（编程范式：组织程序和解决问题的一类方法）通常建立在一个或多个计算模型上，但二者不是普遍同义词。一门现代语言也可能组合命令式、函数式、面向对象、声明式或并发等多种范式。

根据语言判断函数、表达式、状态、对象、消息、关系、协程、任务、Actor 或其他实体扮演什么角色。

### 3. 核心概念体系

建立理解该语言所需的骨干概念及依赖关系，包括但不限于：

- 值、类型、变量、绑定、可变性和相等性；
- 作用域、生命周期、闭包、函数和调用；
- 对象、类、原型、记录或其他数据模型；
- 错误、资源、模块、并发和异步模型。

概念地图只显示关系，详细定义和机制遵循 [concept-first-teaching.md](concept-first-teaching.md)。

### 4. 语言语义

Semantics（语言语义：语言构造在抽象语言层面具有什么含义和可观察行为）回答代码按照语言规则意味着什么。

重点包括：

- 名称怎样解析，值怎样产生和传递；
- 表达式、语句和调用怎样求值；
- 类型规则在什么阶段生效；
- 状态、控制、错误、资源和并发行为怎样变化；
- 哪些结果是规范保证，哪些没有得到保证。

不能用某个常见编译器或 Runtime 的实现方式代替语言语义。

### 5. 工作机制

工作机制用于沿当前抽象层追踪“规则怎样产生结果”，例如：

```text
closure
→ 函数值在后续调用时仍按定义位置的词法关系访问所需绑定

某门语言中的 async/await
→ 按该语言的正式异步模型暂停、保存必要状态并在条件满足后恢复

Rust 中非 Copy 值的 ownership move
→ 值的所有权转移，原绑定不能继续作为该值使用
```

具体实体和规则必须以目标语言的正式模型为准。讲清参与者、初始状态、不变量、事件或调用顺序、状态变化和可观察结果。工作机制可以是解释性的执行模型，不必一开始就下沉到机器指令。

### 6. 编译器与 Runtime 实现

Implementation（实现：编译器、解释器、虚拟机或 Runtime 为实现语言语义所采用的具体数据结构、转换和算法）回答语言行为怎样被实际系统实现。

根据学习目标选择深度：源码到 AST/IR/字节码/机器码、对象布局、栈与堆、垃圾回收、借用检查、调度器或 JIT 等。只有当实现能够解释可观察行为、性能取舍、诊断或语言边界时才展开；同一语义可能有多种合法实现。

对作用域、闭包、对象、状态、控制或类型系统，自己实现一个小解释器有时能让抽象规则变成可观察结构，但不把“写解释器”强制到所有语言主题。

### 7. 语法、常用操作与惯用表达

学习者需要知道概念在真实代码中怎样写，以及完成常见任务需要哪些核心操作：

- 声明、表达式、控制流、函数、类型和模块语法；
- 语言内建类型、集合、标准库和常用 API；
- 参数、返回值、状态影响、错误行为和边界；
- 该语言生态中清晰、自然且可维护的惯用写法。

概念优先不表示把语法和方法压缩成几行。语法结构或操作族的完整讲解读取 [syntax-and-api-teaching.md](syntax-and-api-teaching.md)。

### 8. 工程实践与生态

说明语言特性怎样进入真实工程：

- 模块、依赖、构建、测试、调试、格式化和发布；
- API、状态、错误、资源和并发怎样建模；
- 哪些约束由语言或类型系统保证，哪些仍依赖运行时验证、测试或团队规范；
- 性能、安全、可读性、兼容性和维护成本怎样权衡；
- 什么时候采用当前特性，什么时候替代方案更合适。

具体语言功能不自动等于架构模式或项目规范。工程建议必须说明条件、验证方式和代价。

## 八个维度怎样进入课程

八个维度是整门课程的覆盖检查，不是每章固定重复：

```text
课程导论
→ 设计问题、价值取舍和执行边界

核心模型章节
→ 概念、计算模型、语义和工作机制

语法与标准操作章节
→ 写法、方法契约和惯用表达

进阶实现章节
→ 编译器、Runtime、内存和性能

项目与工具章节
→ 工程实践、生态和综合迁移
```

一个主题可以同时覆盖多个维度；同一维度也可以在课程中逐步加深。使用 [learning-architecture.md](learning-architecture.md) 记录首次讲解位置、前置、后续复用、证据和完成标准。

## 解释一个语言特性

根据范围选择下面的问题，不机械展示全部标题。

### 为什么这样设计

```text
问题与背景约束
→ 设计目标和价值优先级
→ 可行替代方案
→ 最终选择
→ 得到什么、牺牲什么
```

缺少正式设计资料时，可以说明“从现有语义和历史背景推断”，不能把推断写成设计者原话。

### 它实际上怎样工作

```text
准确定义与概念关系
→ 语言语义
→ 可追踪的工作机制
→ 代码、诊断或状态证据
→ 必要时解释具体实现
```

语义先于实现。若实现变化而规范允许的行为不变，教学结论不应依赖偶然实现细节。

### 工程中什么时候使用

```text
真实问题
→ 约束与不变量
→ 语法或操作方式
→ 适用条件
→ 测试与验证
→ 成本、风险和替代方案
```

不要把“语言提供这种能力”直接升级为“项目必须采用这种架构”。

## 跨语言比较

先确定两门语言试图解决的共同问题，再选择会改变结论的维度：

- 实体存在于编译时、运行时还是两者；
- 值、对象、类、原型或记录的关系；
- 类型检查、运行时验证和类型擦除；
- 绑定、作用域、调用、方法查找和派发；
- 生命周期、可变性、资源所有权和清理；
- 错误传播、并发、异步和调度；
- 语言保证、实现行为和工程惯例。

遇到“X 只是语法糖”时，说明它相对于什么目标语义、在哪一层近似成立，以及该说法解释不了哪些行为。不要按关键字相似度直接判定两个概念相同。

## 设计与行为证据

| 要说明的内容 | 优先证据 |
| --- | --- |
| 设计目标和取舍 | 正式设计文档、RFC、语言设计者材料、历史记录 |
| 语言语义和保证 | 规范、标准、官方语言参考 |
| 当前 API 和工具行为 | 当前官方文档、目标版本测试 |
| 编译器或 Runtime 实现 | 官方实现文档、源码、诊断和可重复实验 |
| 工程建议 | 明确场景、约束、测试、数据或成熟项目证据 |

来源不能替代当前解释所需的定义和推理。事实、引用支持的设计理据、教学推断和工程建议应当能够被读者区分。

## 完成条件

整门语言的某一阶段完成，不以“看完语法”或“项目能运行”为准。学习者应在当前范围内能够：

- 说明语言或特性面对的问题和主要取舍；
- 准确定义核心概念并连接到真实代码；
- 根据语义和机制预测新例子的行为；
- 区分语言保证、具体实现和工程约定；
- 使用核心语法和常用操作完成自然任务；
- 比较相邻设计，并说明采用条件、验证方式和代价。
