# 代码与可执行示例规范

讲解编程语言、SQL、API、CLI、配置、测试、调试和算法实现，需要提供可执行证据时使用本规范。本文件约束示例怎样复现、结果怎样呈现和不同保证层怎样区分；语法或 API 应覆盖哪些操作由 [syntax-and-api-teaching.md](syntax-and-api-teaching.md) 决定。

## 通用约定

1. 行为受环境影响时，说明语言、运行时、数据库方言、工具或相关版本。
2. 删除与当前知识点无关的搭建，但完整保留决定输入、调用、结果和状态影响的代码。“最小”不能成为省略核心语法、错误处理或操作契约的理由。
3. 提供必要的输入、初始化、数据或初始状态。
4. 使用带正确语言标识的代码围栏。
5. 明确区分“预期结果”和“实际运行结果”。没有真正执行时，不得暗示代码已经运行。
6. 在代码之后解释关键语句、状态变化和输出。
7. 单一机制覆盖一到两个真正重要的边界；一组具有不同契约的核心操作应分别提供足以验证各自差异的短示例。
8. 伪代码必须标明为伪代码；不可运行内容不能放入具体语言的代码块。
9. 标识符保持一致且有实际含义。
10. 遵守对应语言或生态的惯用规范，不强制所有语言使用同一种排版风格。

代码是讲解的一部分。不要只给出大段代码而不解释为什么会得到当前结果。

## 编译时、运行时与外部输入

涉及类型系统、编译器、转译器、异步或数据边界时，分别标注：

- **编译时保证**：类型检查、静态推导、代码生成或编译器诊断能保证什么；
- **运行时行为**：真正创建了什么对象、发生了什么调用、调度或状态变化；
- **外部输入边界**：网络、文件、用户输入或 `JSON.parse` 等数据为什么不能仅凭静态类型声明变得可信。

把这三层混在一起会让学习者误以为类型标注会在运行时验证数据，或误以为写出 `async`/`await` 就已经解释了协程、任务和调度。示例应在代码旁说明当前证据属于哪一层。

## 用实验形成理解

对机制主题优先采用“先预测、再运行或推演、最后解释”的顺序。展示输出时说明哪些结果受语言规范保证、哪些结果依赖具体运行时或环境；没有实际运行时不要把“预期结果”写成“实际结果”。

## 展示调用结果与状态影响

方法、函数、命令或查询会返回结果或改变状态时，按需同时展示：

```text
调用前状态
→ 调用与参数
→ 返回值或标准输出/错误
→ 调用后状态
```

明确区分：

- 方法本身是否修改接收者；
- 是否创建新值、保留对象身份或分配资源；
- 回调函数是否可能修改元素、外部状态或抛出错误；
- 返回值是否用于链式调用、表示成功/失败，或与修改后的对象不同；
- 输出顺序、迭代顺序和错误行为是否得到规范保证。

不要只写“返回新数组”或“会修改原值”；用具体输入和调用前后结果证明它。

## 注释

注释用于解释意图、约束或不明显的选择。

不要用注释机械复述语法。

较好的注释：

~~~sql
-- 显式排序，避免依赖数据库未保证的默认返回顺序。
SELECT customer_name
FROM customers
ORDER BY customer_id;
~~~

较弱的注释：

~~~sql
-- 查询客户名称。
SELECT customer_name
FROM customers;
~~~

## 安全与正确性

- 外部值使用参数绑定，不把不安全的字符串拼接作为正常示例。
- 资源清理、错误处理、事务边界或资源所有权对当前知识点至关重要时，必须展示。
- 不要省略决定示例是否正确或可运行的代码。
- 有意展示错误代码时，明确标注错误，并紧邻给出修正写法。

## SQL 默认规范

除非目标项目已经采用另一套一致规范，否则默认：

- SQL 关键字使用大写。
- 表名和列名使用小写蛇形命名。
- 持久示例显式选择所需列，不使用 SELECT * 代替查询契约。
- 教学材料显式写出 INNER JOIN、LEFT JOIN 等 JOIN 类型。
- 使用显式 JOIN 语法，不使用逗号分隔表。
- 表之间的匹配关系写在 ON 中，结果过滤写在 WHERE 中；讲解 LEFT JOIN 等外连接时，必须说明条件位置可能改变语义。
- 主要子句分行书写。
- 多表查询限定列来源。
- 使用简短但有意义的别名，并保持一致。
- 示例结果需要稳定顺序时添加 ORDER BY。
- SQL 语句以分号结尾。
- 数据类型、函数、字面量或行为依赖方言时，说明具体 SQL 方言。

示例：

~~~sql
SELECT
    c.customer_id,
    c.customer_name,
    o.order_id,
    o.total_cents
FROM customers AS c
INNER JOIN orders AS o
    ON o.customer_id = c.customer_id
WHERE o.total_cents >= 5000
ORDER BY
    c.customer_id,
    o.order_id;
~~~

讲解 JOIN 时，提供足够的表结构和示例数据，使行匹配、重复、未匹配行和 NULL 行为能够被直接观察。

区分 SQL 的逻辑语义与物理执行方式。查询优化器可以选择与文本顺序不同的连接顺序或算法，只要保持逻辑结果等价。

## 展示结果

小型表格结果使用 Markdown 表格，终端输出使用文本代码块。

解释：

- 哪些行或值会出现。
- 哪些行或值不会出现。
- 哪个谓词或状态变化造成该结果。
- 当前顺序是否得到保证。

## 算法示例

讲解算法时：

1. 说明输入和输出。
2. 解释核心思想。
3. 手工推演一个具体例子。
4. 用户要求或实现有助于理解时，提供规范代码。
5. 说明时间和空间复杂度及其前提。
6. 覆盖边界情况和正确性直觉。

不能只给出复杂度，并把它当成实际性能的完整描述。
