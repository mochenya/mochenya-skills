# Obsidian 交付规范

本参考文件定义可学习架构笔记的共同形状。按主题复杂度删减，不为模板填空。

## 1. 推荐笔记集合

普通项目使用“总览 + 机制模块 + 迁移模式”。Agent 项目可以使用以下 9+1 基线：

```text
00 总览
01 架构与进程模型
02 Agent Loop
03 上下文工程
04 工具系统
05 记忆系统
06 自进化闭环
07 委派、并行与自动化
08 网关与多平台
09 可迁移设计模式与取舍
```

小项目将没有独立心智模型的主题合并；大项目按真实边界增加笔记。UI、皮肤和纯展示层默认不进入这组核心笔记。

## 2. Frontmatter

每篇笔记使用稳定、少量、可检索的元数据：

```yaml
---
title: "主题名称"
aliases: ["alternate name"]
tags: ["cs/ai-agent", "swe/architecture"]
type: "architecture"
repo: "owner/project"
commit: "short-or-full-sha"
version: "project-version-or-unknown"
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
---
```

如果项目没有版本，写 `unknown`，不要猜。`commit` 应对应实际分析的 checkout。

## 3. 每篇笔记的解释链

推荐顺序：

1. 用一句话给出结论和本篇边界。
2. 写“它要解决什么问题”，不要从文件名开始。
3. 建立概念图，首次引入核心术语时给出英文正式术语、中文规范译名和准确的一句话定义。
4. 解释生命周期、控制流、数据流或状态转换。
5. 放 3–6 个最有价值的源码摘录，覆盖入口、核心机制、边界或失败路径。
6. 用 Mermaid 表达复杂关系，并在图后逐步解释。
7. 总结接口契约、不变量、缓存/持久化边界、失败处理和未验证项。
8. 连接工程迁移和相邻笔记，最后给出能检验理解的自检问题及成功答案。

## 4. 源码摘录规则

- 使用仓库相对路径和起始行号，例如 `agent/conversation_loop.py:2029`。
- 摘录保留源码语义、缩进和关键上下文；不把改写的伪代码放入 `python` 源码围栏。
- 为了聚焦而省略源码时写 `...`，并在摘录前说明它是片段。
- 代码下方解释 receiver、参数、返回值、状态变化、调用边界和失败路径；不要只翻译语法。
- 运行过的结果写“实际观察”；没有运行条件时写“预期”或“待验证”。

## 5. Mermaid 选择

- 组件依赖用 `flowchart`，外部输入到响应用 `sequenceDiagram`，状态变化用 `stateDiagram-v2`。
- 标签保持短小，避免在节点标签中嵌套复杂括号、引号或多行 Markdown。
- 图不能替代定义、代码和机制说明；每张图只解决一个主要认知问题。

## 6. 链接与自检

使用 Obsidian wikilink 连接同一分析集：

```markdown
相关笔记：[[02-Agent-Loop-回合生命周期]]、[[04-工具系统-注册发现与调度]]
```

自检问题应要求读者定义、预测、解释、定位或迁移，而不是复述标题。每个问题后给出简短成功答案或定位线索，避免把笔记变成没有反馈的问卷。
