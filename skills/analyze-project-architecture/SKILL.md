# 项目架构分析

把陌生仓库转化为可独立阅读、可验证、可迁移的架构知识库。核心结果不是文件清单，而是回答：系统解决什么问题、真实入口在哪里、控制流和数据流怎样经过各层、模块之间的契约是什么、哪些设计取舍值得迁移。

## 适用边界

- 用户要求阅读仓库、理解系统架构、拆解 Agent 模块、生成流程图或 Obsidian Markdown 时使用。
- 普通实现、修 bug、代码审查、只要 API 用法的请求不自动套用本 Skill。
- 只分析用户指定的仓库和范围；不因发现周边产品、UI、部署或商业模块而擅自扩大范围。
- 默认把 UI、皮肤和纯展示层排除在核心架构笔记之外，除非用户明确要求。

## 工作协议

1. 先读取仓库内适用的 `AGENTS.md`，再读取 README、项目元数据、目录拓扑和官方架构文档。把版本、commit、日期和分析范围写入证据记录。
2. 先建立总览，再追踪至少一条真实生命周期：启动、请求进入、核心循环、外部调用、状态持久化、响应交付和收尾。不要从模块名直接推断架构。
3. 按责任边界拆解模块。每个模块都说明问题、输入输出、状态、不变量、错误路径、源码证据和与相邻模块的契约。
4. 复杂任务可以按互不重叠的研究包委派给子 Agent；为每个研究包规定文件范围、问题、证据格式和禁止越界的范围。没有可用委派工具时，主 Agent 必须按同样的研究包自我拆解，不能虚构子 Agent 回传。
5. 先写核心概念和机制，再写 API 或文件细节。核心术语首次出现使用 `English formal term（中文规范译名：它是什么）`，源码标识符保留原样。
6. 最后把源码事实、官方文档、仓库指南和推断分层；发现不一致时记录“代码事实 / 文档说法 / 影响”，不能静默选择一个版本。

详细勘察步骤见 [references/repository-exploration.md](references/repository-exploration.md)。

## 默认交付物

优先生成一组互相链接的 Obsidian Markdown，而不是一篇超长报告：

- `00` 总览：定位、边界、组件地图、主流程、阅读路线和关键结论。
- `01` 架构与进程模型：入口、运行模式、进程边界、核心依赖和生命周期。
- 中间模块笔记：按仓库实际机制选择 Agent Loop、上下文、工具、记忆、自进化、委派/自动化、网关/适配器等主题。
- 最后一篇迁移笔记：可复用模式、替代方案、成本、风险和适用条件。

对 Agent 项目可采用“9+1”基线：总览、架构与进程模型、Agent Loop、上下文工程、工具系统、记忆系统、自进化闭环、委派与自动化、网关与多平台、可迁移设计模式。规模较小的仓库应合并主题，不为凑篇数拆分。

每篇实质性模块笔记通常保留 3–6 个最有解释力的源码摘录；不是机械复制代码。摘录必须标注仓库相对路径和起始行号，省略部分显式写成 `...`，不能把改写后的伪代码冒充源码。

Obsidian 写作和笔记模板见 [references/obsidian-output.md](references/obsidian-output.md)。

## 证据与验证

- 优先以 checkout 中的源码和测试为事实来源；使用官方文档解释设计意图，不能用文档替代代码验证。
- 对动态行为区分“源码显示”“实际执行”“合理推断”“待验证”，没有运行条件时不得声称观察到了运行结果。
- Mermaid 只表达真正复杂的关系、时序、状态或数据流；图下必须有文字解释、关键不变量和边界。
- 每篇笔记必须有问题、定义、机制、证据、工程迁移和自检问题；相关笔记通过 `[[wikilinks]]` 连接。
- 完成后运行 `scripts/validate_architecture_notes.ps1`，检查 frontmatter、代码围栏、Mermaid、内部链接和源码行号。验证规范见 [references/verification-checklist.md](references/verification-checklist.md)。

## 版本与外部资料

如果用户询问依赖库、框架、SDK、API 或 CLI 的当前用法，按环境规定查询 Context7 或对应权威文档；但项目内部架构结论仍以固定 checkout 的源码为准。记录外部资料的版本或访问日期，避免把当前资料误写成仓库历史事实。
